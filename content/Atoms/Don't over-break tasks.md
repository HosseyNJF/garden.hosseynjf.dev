When you're in charge of turning key results to definitive actions and definition-of-dones (DoDs), don't break tasks to the finest detail you could think of. Software Engineering tasks should be broken to as small parts as possible, but don't break a task into a few sections, and then find out that they're so coupled together that only one person can do it anyway.

Here's some criteria that might help you figure out the boundaries of different tasks in a user story:

- Tasks that are in sequential order and may be deeply coupled with previous step's code
- Tasks that are already reasonably small (can be done by a single engineer in a couple of days)
- Tasks that seem easy to break but it would be more efficient for one person to do it - Context is really important in these kind of tasks
